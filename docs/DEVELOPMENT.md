# 開発・検証ガイド

この文書は開発者向けの実行方法、内部設計、各フェーズの実装内容をまとめたものです。
利用者向けの説明は [README](../README.md) を参照してください。

## 実行方法

Node.js 20.19+ または 22.12+（検証環境: 24.19）を使用します。

```sh
npm ci
npm run dev -- --host 0.0.0.0
npm test
npm run build
npm run preview -- --host 0.0.0.0
```

画像を選択するかプレビュー領域に1枚ドロップし、画像上をクリックします。
元画像のピクセル座標で衝撃点を保持し、ウィンドウサイズが変わっても位置を維持します。
余白のクリックは無視し、別画像の読み込み時には衝撃点をリセットします。
画像読み込みに失敗した場合は前の画像を保持します。

## Phase 2: 生成エンジン

画像上の各衝撃点から放射状・同心円状・分岐状の亀裂を表示します。
リサイズは再描画だけを行い、元画像座標の幾何データを維持します。

`generateCracks(size, origin, seed, params)` は DOM に依存しない純粋関数です。
同じ入力は同じ線分データを返します。シードは安全な整数を受け付け、PRNG 内部では
uint32 に正規化します（2^32 差のシードは同じ系列です）。

- 主要亀裂数: 4〜24
- 長さ: 画像短辺の10〜150%
- 複雑さ・同心円密度: 0〜100（0ではそれぞれ分岐・同心円を生成しません）
- 線分数上限: 1〜5000。全種類の合計に適用し、放射状→同心円状→分岐状の順に格納
- 全線分を画像矩形にクリッピングし、長さゼロの線分を除外

生成と描画は分離し、描画処理は乱数を使用しません。
画像サイズ上限の機種別検証とキーボードによる衝撃点指定は今後の課題です。

## Phase 3: 編集UI

1. 画像を選択し、「追加」モードで画像上をクリックすると衝撃点が増えます。
2. マーカーまたは「衝撃点を選択」から編集する点を選びます。選択点は緑、他の点は黄色です。
3. マーカーをドラッグするか、「移動」モードで画像をクリックして選択点を移動します。
4. 「選択した衝撃点を削除」でその点だけを削除します。全削除後は追加モードに戻ります。
5. 各点に独立した Realistic / Anime プリセット、設定、シードを保持します。

調整できる項目は主要亀裂数（4〜24本）、長さ（10〜150%）、複雑さ・同心円密度（0〜100%）、
線幅（0.5〜6元画像px）、不透明度・ハイライト（0〜100%）、シード（安全な整数）です。
スライダー操作ではシードを保持し、線幅・不透明度・ハイライトの変更では幾何形状を再生成しません。
「再生成」は選択点のシードを uint32 として1つ進めます（最大値の次は0）。
元の設定・シード・座標へ戻すと同じ形状を再現できます。

新規点は Realistic・シード1で始まります。プリセット切り替えでは調整値を初期化しますが、
位置とシード、他の衝撃点の設定は保持します。Realistic は細線・多めの分岐、Anime は
太線・少なめの主要亀裂を初期値とします。描画は以下の Phase 4 のスタイルを使用します。
別画像を読み込むと全点をリセットし、読み込み失敗時は編集中の画像と点を保持します。

## Phase 4: 表現品質

- **Realistic**: 細い主要線とさらに細い分岐・同心円、控えめなハイライト（初期値25%）。
- **Anime**: 主要亀裂を太く、遠方ほど細くして線幅の強弱を強調。明瞭な輪郭と強めのハイライト（65%）。
- 明るい画像では暗い輪郭、暗い画像では淡い芯と白いハイライトで視認性を確保します。
- 線幅は元画像px基準の主要線の基準値です。線種・距離によって細くなります。
- 不透明度0では輪郭・芯・ハイライトを全て非表示にします（編集マーカーは表示）。
- スタイル描画はシードや幾何データを変更せず、全描画を画像境界にクリッピングします。

[比較画像](phase4-comparison.png)は、同じ幾何形状・シード42・基準線幅3px・不透明度85%を使い、
明るい背景・暗い背景・透過画像で描画したものです。各プリセットの初期値を使用すると、
これに加えて亀裂数・分岐量・同心円密度も変わります。

開発用の比較ページは `npm run dev` を実行して
`/mirror-crack-generator/tests/visual.html` を開くと再現できます。
サンプルPNGは `docs/samples/`（リポジトリルート基準） にあり、外部画像や外部サービスを使用しない自作テスト素材です。
比較ページは開発用で、通常の本番ビルドには含めません。

## Phase 5: PNG出力と品質

画像読み込み後、画像パネルの出力ボタンから保存できます。

- **合成PNGを保存**: 元画像に全ての衝撃点の亀裂を重ねます。
- **亀裂のみPNGを保存**: 元画像を含めず、背景透明の亀裂レイヤーを保存します。
- 出力サイズは元画像と同じピクセル寸法です。プレビューの表示倍率や端末のDPRに依存しません。
- 画像の余白・マーカー・点番号は含めません。合成PNGの非亀裂領域は元画像のアルファを保持します。
- 不透明度0の点は出力されません。点がない場合は、合成PNGは元画像、亀裂のみPNGは完全透明です。
- 保存名は `元ファイル名-composite.png` / `元ファイル名-cracks.png` です。
- 保存開始時点の画像と設定を使用します。保存中の編集は次回の出力へ反映されます。

対応上限はファイル64MiB、一辺8,192px、総画素数16,777,216です。
これはメモリ使用量を抑えるための上限で、全機種での動作保証値ではありません。
上限超過は説明を表示し、編集中の画像・衝撃点を保持します。
Canvasの確保やPNG変換に失敗した場合もエラーを表示し、画像を小さくして再試行できます。
書き出し用Canvasは処理後に解放します。画像や出力PNGをサーバーへ送信しません。

`npm test` はサイズ上限・ファイル名・座標変換・生成・編集状態などの単体テストを実行します。
実際のPNGの読み戻し検証は、`npm run dev` 実行後に
`/mirror-crack-generator/tests/export.html` を開くと再実行できます。
元解像度・透明/半透明・座標一致・マーカー除外・複数点・不透明度0・
過大画像の拒否・Canvas/PNG変換失敗後の回復を検証します（開発専用で本番配信には含みません）。
Chromiumで2048×1024画像の出力と、DPR2での800×600画像の両モードのダウンロードを検証済みです。
実際のイラストソフトへの取り込みやSafari/Firefox、上限サイズ付近の機種別検証は残っています。

## GitHub Pages への公開

GitHub の Settings → Pages → Build and deployment → Source を **GitHub Actions** に設定します。
`main` への push ごとに `.github/workflows/deploy-pages.yml` がテストとビルドを実行し、
`dist` を公開します。設定変更後は Actions の「Deploy GitHub Pages」から
「Run workflow」を実行して再公開することもできます。

公開URL: https://tokimeki-marinosuke.github.io/mirror-crack-generator/

Vite の `base` は `/mirror-crack-generator/` に設定しています。
ソースの `index.html` を直接配信せず、必ずビルド済み `dist` を配信してください。
ローカルの開発・プレビューでも `/mirror-crack-generator/` を開きます。

## 中心制御とアルゴリズム比較

中心半径・密度の仕様と乱数系列の分離は [設計](../ARCHITECTURE.md#生成アルゴリズム改善) を参照してください。
中心密度は整数プリセットで分岐せず、固定された候補の出現強度を連続的に変更します。
中心密度0では全線分とその太さ・ハイライトを円外に制限します。

`npm run dev` 実行後、`/mirror-crack-generator/tests/algorithm.html` で旧版と新版を比較できます。
`tests/fixtures/generateCracks.v1.ts` は旧版の比較専用スナップショットで、本番バンドルには含めません。
[比較画像](algorithm-comparison.png)は共通のシード42、主要線12本、長さ80%、複雑さ55%、網目45%、
描画線幅3pxを使用し、新版のみ中心半径25%、密度0/50/100%を指定しています。

`centerCracks.test.ts` は中心円と線分の最短距離、外側の完全一致、密度の連続変化、
上限・境界・極端な設定を検証します。PNGの実ブラウザテストには中心のRGBA保護も含みます。
全ての線分の交差除去や完全な破片グラフの構築は行っていません。
